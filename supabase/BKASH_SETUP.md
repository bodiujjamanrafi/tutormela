# bKash connection checklist

The integration is prepared and intentionally disabled. No live merchant credentials were supplied. The frontend never asks for a wallet PIN/OTP and never activates a plan from a browser success message.

1. Existing project: apply `subscription-and-profile-setup.sql`. This includes the earlier pending posting rules and the new payment order storage. Independent identity storage is already applied to the live project. Fresh project: run `schema.sql`. All scripts can be rerun without deleting posts or accounts.
2. Obtain merchant credentials and confirm **Tokenized Checkout v1.2.0-beta without agreement** with bKash. This adapter does not support Tokenized V2; adapt and retest it if your merchant account is issued V2. Official merchant reference: https://developer.bka.sh/docs/tokenized-checkout-overview and https://github.com/bKash-developer/bKash-for-woocommerce .
3. Add server-only Supabase Edge Function secrets: `BKASH_APP_KEY`, `BKASH_APP_SECRET`, `BKASH_USERNAME`, `BKASH_PASSWORD`, `BKASH_CALLBACK_SECRET` (a unique random value at least 32 characters), `BKASH_ENVIRONMENT=sandbox`, `BKASH_API_VERSION=v1.2.0-beta`, and `BKASH_ENABLED=true`. Set `APP_ORIGINS` to the exact allowed website origins, comma separated. Never prefix any secret with `VITE_`, commit it, or paste it into chat.
4. Deploy `bkash-checkout` with gateway JWT verification disabled because bKash's callback has no user JWT. POST requests independently validate the user token with Supabase Auth and the verified-session RPC. GET callbacks require a signed order reference. Keep these checks intact.
5. Register the callback URL with bKash: `https://zpjdlkrtscxyucqudbpd.supabase.co/functions/v1/bkash-checkout` (query parameters are added per order). The callback returns to the original, allowlisted website origin.
6. Run bKash merchant sandbox acceptance tests: success, wrong OTP, insufficient funds, cancel, timeout, duplicated callback, different user reading an order, and forged browser success. Sandbox payments are recorded but **never grant a real paid allowance**. Status must be confirmed from bKash with matching payment ID, invoice, BDT amount and transaction ID. Run `node scripts/verify-identity-bkash.js` and the Deno gateway test first.
7. After bKash acceptance and approval, set live credentials and `BKASH_ENVIRONMENT=live`, rerun a controlled live purchase, and check the verified order and subscription. These are one-month purchases, **not automatic recurring charges**. Active subscriptions block a second purchase to avoid overlapping charges.

A unique order and execution claim make callbacks idempotent. Ambiguous execute timeouts use query-payment, never another execute call. If bKash completes a charge but settlement cannot be confirmed, leave it pending and reconcile through the authenticated status check; do not tell a customer to pay again. Gateway API failures and credentials are never returned to the browser or logged.

Published teaching posts and their metrics remain separate from `tm_accounts.tutor_identity`. Saving identity is atomic, preserves private phone/preferences, and does not overwrite or publish a post.
